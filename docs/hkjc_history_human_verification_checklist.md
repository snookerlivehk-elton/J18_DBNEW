# HKJC 歷史補充資料人工核實清單

本清單用於列出在正式交由 Trae AI 長流程自主開發前，最適合由人工先完成核實、測試、確認或拍板的項目。  
目標是先把高風險、不確定、容易令 AI 卡住或做錯決策的事項排除，之後再讓 AI 依手冊持續開發。

---

## 1. 使用方式

- 先由人工逐項檢查本清單。
- 每一項如已確認，請記錄明確結論，而不是只寫「應該可以」。
- 若某項仍未確認，先不要讓 AI 對該部分做最終實作決策。
- 建議把人工確認結果補回主手冊或另存於同一 `docs/` 目錄。

---

## 2. 優先級說明

- `P0`：必須先人工確認，否則 AI 很大機會走錯方向
- `P1`：高度建議人工先確認，否則 AI 容易中途卡住或反覆修改
- `P2`：可於中後期再人工確認，但最好提前知道答案

---

## 3. P0 必須先人工核實

### 3.1 馬匹歷史頁的真實入口與參數格式

- [ ] 確認 HKJC 馬匹歷史頁的實際 URL 格式
- [ ] 確認進入馬匹歷史頁是否只需 `horse_id`
- [ ] 確認是否需要額外 query string、season、lang 或 hidden state
- [ ] 確認歷史頁是否需要點擊分頁才能看到完整歷史
- [ ] 確認歷史頁是否有最多顯示筆數限制

**人工應提供給 AI 的結果**

- 至少 2 至 3 個可重現的馬匹歷史頁真實 URL
- 每個 URL 對應的 `horse_id`
- 是否有分頁、載入更多、或 season 切換規則

**為什麼必須人工先做**

- 目前手冊已定義了整個系統要「以馬找場」，但真正最關鍵的起點仍是馬匹歷史頁。
- 只要這個入口格式不明，AI 後續所有 backfill 流程都可能建在錯誤假設上。

---

### 3.2 `horse_id` 在各來源頁是否穩定一致

- [ ] 確認 `horse_id` 在馬匹歷史頁、競賽事件報告、沿路走勢評述、分段時間頁是否可穩定對上
- [ ] 確認同一匹馬在不同頁面顯示的 `horse_id` 是否完全一致
- [ ] 確認是否存在只有 `horse_code` 但沒有 `horse_id` 的頁型
- [ ] 確認 `horse_name + horse_code` 是否可作備援匹配

**人工應提供給 AI 的結果**

- 一組同一匹馬在不同來源頁的實際對照例子
- 明確結論：是否能以 `horse_id` 作為第一主鍵

**為什麼必須人工先做**

- 這是整套系統最核心的對齊鍵。
- 若此處不穩，AI 可能會誤做大量 fallback matching，風險極高。

---

### 3.3 `分段排名` 是否真的存在可直接來源

- [ ] 確認 HKJC 哪個頁面或哪種顯示模式能直接取得「馬匹分段排名」
- [ ] 確認目前已知的 `displaysectionaltime` 頁面是否只提供位置 / 頭馬距離 / 分段時間，而不提供真正排名
- [ ] 確認是否需要切換語言、模式、按鈕或另一個頁面才看得到排名
- [ ] 確認第一版是否接受 `horse_section_rank_1 ~ 6` 全部先填 `null`

**人工應提供給 AI 的結果**

- 一個「有直接分段排名」的實際頁面證據，或
- 一個明確結論：第一版沒有直接來源，全部先填 `null`

**為什麼必須人工先做**

- 若這一點不先拍板，AI 很可能會花大量時間嘗試從位置或時間推導排名，導致規格偏離。

---

### 3.4 馬匹歷史頁中的「歷史場次完整度」是否足夠

- [ ] 確認馬匹歷史頁是否真的涵蓋你要補的歷史範圍
- [ ] 確認是否只顯示近季賽事，還是可追到更舊賽季
- [ ] 確認是否需要切 season 才能看完整歷史
- [ ] 確認是否有海外賽事、試閘、特殊賽事混入

**人工應提供給 AI 的結果**

- 明確說明「系統第一版要抓的歷史範圍」
- 例如：
  - 只抓香港本地正式賽事
  - 不抓 trial / barrier trial
  - 不抓海外賽事

**為什麼必須人工先做**

- 這會直接影響 `horse_race_history` 的來源過濾規則與場次任務生成。

---

### 3.5 反爬、頻率限制與封鎖風險

- [ ] 人工測試連續抓取多個 HKJC 頁面是否會觸發限制
- [ ] 確認是否有 403、429、captcha、地區限制或短時間封鎖
- [ ] 確認同一來源頁是否適合高併發抓取
- [ ] 確認是否需要保守節流、重試間隔與 user-agent 策略

**人工應提供給 AI 的結果**

- 明確的抓取節奏建議
- 例如：
  - 單場間隔多少秒
  - 是否禁止高併發
  - 是否應加 retry/backoff

**為什麼必須人工先做**

- AI 若不知道實際風險，可能用過高頻率自動掃頁，導致整體抓取失敗。

---

## 4. P1 高度建議人工先核實

### 4.1 特殊名次與異常賽果值

- [ ] 確認 `finish_position` 是否只會是整數
- [ ] 確認是否存在 `UR`、`PU`、`DNF`、退出、取消資格等特殊值
- [ ] 確認這些特殊值在 HKJC 頁面中出現在哪些來源
- [ ] 決定第一版是否保留原文欄位或另外拆規則

**原因**

- 若 AI 先假設名次全為整數，後面遇到特例會導致 parser 或欄位型別修改。

---

### 4.2 預期馬匹數的基準

- [ ] 確認某場「預期馬匹數」應以 `horses_v2` 為準還是 HKJC 當場頁面為準
- [ ] 確認退出馬匹是否算在預期馬匹數內
- [ ] 確認賽果頁與報告頁若筆數不一致，哪個才是 QA 基準

**原因**

- 這直接影響 `partial / success / failed` 的判定。

---

### 4.3 是否需要第一版就提供 API 入口

- [ ] 確認第一版是否只需要 script / CLI
- [ ] 確認是否一定要在 `main.py` 增加 API
- [ ] 確認 UI 是否需要同步調整

**原因**

- 若不先拍板，AI 可能同時做 schema、script、API、UI，範圍容易失控。

**建議人工拍板**

- 第一版先只做 script 與資料層
- API / UI 延後

---

### 4.4 是否接受第一版不做內容覆寫

- [ ] 確認第一版正式策略是否為 `只新增，不覆寫`
- [ ] 確認即使來源頁內容後續更新，也先不處理版本更新
- [ ] 確認之後若要支援更新，再做第二版規格

**原因**

- 這會大幅影響 CRUD 設計、registry 行為與 QA 流程。

---

### 4.5 是否允許 AI 新增 service / helper 模組

- [ ] 確認 AI 是否可在 `src/j18_dbnew/` 下新增 `services/` 或 `utils/` 類模組
- [ ] 若不希望新增太多模組，請明確限制只能用既有目錄：
  - `db/`
  - `parsers/`
  - `scrapers/`
  - `scripts/`

**原因**

- 不先限制，AI 可能因為分層習慣自行新增太多結構，影響後續維護。

---

## 5. P2 建議中期人工核實

### 5.1 UI 展示需求是否需要納入第一版

- [ ] 確認是否要在 `templates/index.html` 加入補充資料展示
- [ ] 確認是否只需要 DB 成功寫入即可，不要求 UI

---

### 5.2 完成率報表與缺漏追蹤是否要提前做

- [ ] 確認第一版是否就要做完成率報表
- [ ] 確認第一版是否就要做缺漏場次查詢頁或 API

---

### 5.3 研訊摘要、獸醫標記、裝備變更是否先不做

- [ ] 確認這三項全部延後至第一版完成後
- [ ] 確認 AI 不應在第一版主流程中主動擴充這些功能

---

## 6. 建議人工提供的「黃金測試樣本」

在你正式交給 AI 前，建議你手動整理一個小型樣本集，供 AI 開發與驗證使用。

### 6.1 建議至少提供以下樣本

- [ ] 2 匹馬的真實馬匹歷史頁 URL
- [ ] 2 個賽日的 `競賽事件報告` URL
- [ ] 2 個場次的 `沿路走勢評述` URL
- [ ] 2 個場次的 `分段時間及位置` URL
- [ ] 至少 1 場只有 5 段的樣本
- [ ] 至少 1 場有 `無特別報告。` 的樣本
- [ ] 至少 1 場有特殊文字描述的 incident report 樣本

### 6.2 最好再補的樣本

- [ ] 1 場有明顯 `partial` 風險的頁面
- [ ] 1 匹歷史頁含多個 season 或很多歷史紀錄的馬
- [ ] 1 場含退出、後備、特殊名次或異常欄位的樣本

---

## 7. 建議你先人工拍板的決策

以下事項只要你先拍板，AI 自主開發時會穩很多：

- [ ] 第一版是否只做 script，不做 API / UI
- [ ] 第一版是否只新增，不覆寫
- [ ] 第一版 `horse_section_rank_1 ~ 6` 是否全部允許先填 `null`
- [ ] 第一版是否不做 NLP、摘要、事件抽取
- [ ] 第一版是否只抓香港本地正式賽事
- [ ] 第一版是否不抓海外賽事 / 試閘 / 非正式賽事
- [ ] 第一版是否不處理版本更新
- [ ] 第一版是否禁止 AI 自行擴張 scope

---

## 8. 人工核實完成後，建議交給 AI 的材料

建議最少一併提供給 Trae AI：

- [ ] `docs/hkjc_history_data_development_manual.md`
- [ ] `docs/hkjc_history_v1_implementation_checklist.md`
- [ ] `docs/hkjc_history_v1_task_checklist.md`
- [ ] 本文件 `docs/hkjc_history_human_verification_checklist.md`
- [ ] 你人工核實後整理的測試樣本 URL 與結論
- [ ] 明確的一句話指令：
  - 例如：`請嚴格依 docs 內手冊與 checklist 逐步完成第一版開發，不得擴張 scope；若遇到本文件列為人工核實項而尚未確認者，先停止該部分實作並整理阻塞點。`

---

## 9. 建議最終狀態

當以下條件都成立時，就比較適合交由 AI 自主長流程開發：

- [ ] 馬匹歷史頁入口已人工確認
- [ ] `horse_id` 對齊規則已人工確認
- [ ] `分段排名` 是否有直接來源已人工拍板
- [ ] 歷史資料範圍已人工界定
- [ ] 抓取頻率限制已人工測過
- [ ] 第一版 scope 已人工鎖定
- [ ] 黃金測試樣本已備妥

---

## 10. 一句話總結

在正式交由 AI 自主開發前，人工最應優先確認的不是程式怎樣寫，而是：

- 真實資料入口是否正確
- 主鍵是否穩定
- 哪些欄位有直接來源、哪些欄位不能推導
- 第一版 scope 到底停在哪裡

只要這 4 類問題先由你人工拍板，AI 後續長流程自主完成的成功率會高很多。
